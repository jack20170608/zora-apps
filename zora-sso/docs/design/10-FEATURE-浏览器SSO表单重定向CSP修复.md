# 浏览器 SSO 表单重定向 CSP 修复

## 问题与复现

HTTP Client 可以完成分步认证，但 Chrome 在提交登录表单后报告违反 `form-action 'self'`，页面停留在 SSO 登录页。

登录表单提交到 SSO 自身的 `/login`，成功后通过 302 跳转到应用回调。SSO 与应用使用不同端口，属于不同源。Chrome 会检查表单提交后的重定向目标，原策略仅允许同源，因而阻断跨源回调。HTTP Client 不执行浏览器的 CSP 检查，所以原有 HTTP 测试无法发现这一问题。

该问题已通过独立的无头 Chrome 会话在本地复现，不是仅根据响应头推测。

## 修复方案

- `LoginPage` 增加 `redirectUri`，由核心服务从已校验的登录事务读取。
- 登录页与成功登录响应的 `form-action` 允许 `'self'` 和当前事务回调 URI 的来源。
- 来源保留协议、主机和端口，不包含路径、查询参数、授权码或 state。
- 只接受具有有效主机且不含用户信息的 HTTP(S) 来源。
- 授权失败与其他响应仍使用原来的严格策略。

例如，已校验回调为 `http://localhost:8000/auth/sso/callback` 时，登录相关响应允许的表单目标为 `'self' http://localhost:8000`。

不使用通配符，不移除 CSP，不从登录页查询参数直接读取允许来源，也不放行同一客户端的其他未选中回调来源。注册回调 URI 的精确匹配、CSRF、state 和授权码一次性校验保持不变。

## 测试覆盖

HTTP 集成测试检查以下行为：

1. 登录页与成功登录响应包含当前回调来源。
2. 本地回调来源保留显式端口。
3. 登录页额外提供的攻击者 `redirect_uri` 参数不能改变策略。
4. 同一客户端的其他已注册来源不会被同时放行。
5. 未注册的回调地址仍被拒绝，并保留严格 CSP。

运行全部测试：

```bash
mvn -f zora-sso/pom.xml test
```

修复验证时共运行 22 项测试，21 项通过、1 项跳过。新增回归断言在旧实现下失败，修复后通过。

另外，在独立端口启动编译后的 SSO，使用 Chrome 提交真实登录表单，并跳转到另一个端口的测试回调服务器。回调包含授权码和匹配的 state，且没有 CSP 错误。该浏览器检查验证跨源登录跳转，不代替 host-helper 后端授权码兑换的端到端测试。

## 更新运行中的服务

1. 重新构建并重启 zora-sso，确保接口、核心服务和 Web 适配器使用同一版本。仅修改源码不会改变已运行服务的响应头。
2. 从 host-helper 首页开始新的登录流程，不复用旧的登录事务、state 或授权码。
3. 在浏览器开发者工具中打开 Network，并启用 Preserve log。
4. 确认登录页的 CSP 包含当前应用回调来源。
5. 确认提交登录表单后到达应用回调，并最终进入首页，Console 不再出现 `form-action` 拦截。

如需排除历史 Cookie，可使用新的无痕窗口。不要通过禁用浏览器安全检查或放宽到任意来源解决此问题。
