# 浏览器 SSO 与会话

## 1. SSO 的本质

SSO 不是多个应用共用一个 Cookie，而是多个应用信任同一个身份提供方：

```text
身份提供方中央会话
        |
        +-- 应用 A 完成协议回调 -> 应用 A Session
        +-- 应用 B 完成协议回调 -> 应用 B Session
```

用户访问应用 B 时仍会经历授权请求和回调，只是身份提供方发现中央会话有效，因此不再要求输入密码。

## 2. 三类状态

| 状态 | 保存位置 | 生命周期 |
|---|---|---|
| 授权事务 | RP 或 OP 服务端 | 分钟级、一次性 |
| 中央会话 | 身份提供方 | 受空闲与绝对超时约束 |
| 应用会话 | 各业务应用 | 由应用独立管理 |

授权事务保存 `state`、`nonce`、PKCE verifier、原始访问地址等短期数据。它不能被中央会话替代。

## 3. Session 生命周期

至少同时考虑：

- **Idle timeout**：持续无活动后过期；
- **Absolute timeout**：无论是否活跃，到点必须重新认证；
- **Rotation**：登录和权限提升后更换 Session ID；
- **Revocation**：账号禁用、密码重置或风险事件后主动失效；
- **Concurrency**：是否限制同一用户并发会话。

服务端应存储 Session ID 摘要，Cookie 中仅放高熵随机值。不要把敏感用户信息直接编码进普通 Session Cookie。

## 4. 登出不是一个动作

| 类型 | 结果 |
|---|---|
| 本地登出 | 仅删除当前应用 Session |
| RP 发起登出 | 应用请求身份提供方结束中央会话 |
| 前/后通道登出 | 身份提供方向其他应用传播登出 |
| 全局撤销 | 同时处理中央会话、应用会话和长期 Token |

系统必须明确产品语义。“退出应用”不一定等于“退出所有系统”，静默失败会造成错误安全预期。

## 5. 多节点与故障

生产环境需要决定：

- 会话存储是集中式、粘性会话还是无状态 Token；
- 缓存或身份提供方不可用时是拒绝访问还是允许有限降级；
- 密钥轮换、会话撤销如何跨节点传播；
- 时钟偏差和网络超时如何设置。

认证与授权默认应失败关闭。不能因为身份系统暂时不可用，就自动创建匿名以上权限的身份。

## 6. 检查点

能区分中央会话、应用会话和授权事务，并能说明本地登出与全局登出的差异。
