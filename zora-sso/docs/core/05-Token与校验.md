# Token 与校验

## 1. Token 的两种常见形态

- **引用型 Token**：随机字符串，资源服务器通过 Introspection 或共享存储查询状态。
- **自包含 Token**：常见为 JWT，资源服务器本地验证签名与 Claims。

JWT 降低每次远程查询成本，但撤销更难；引用型 Token 易集中控制，但增加网络依赖。选择取决于撤销时效、吞吐量和故障模型。

## 2. JWT 验证顺序

安全验证不是“Base64 解码后读取角色”：

1. 限制 Token 大小和结构；
2. 只允许配置中的算法，拒绝 `none` 和算法降级；
3. 从可信 JWKS 中选择密钥并验证签名；
4. 精确校验 `iss`；
5. 校验 `aud` 面向当前服务；
6. 校验 `exp`、`nbf`、`iat`，时钟容差应小且固定；
7. 按 Token 类型校验 `nonce`、`azp`、Scope 等；
8. 最后才映射本地身份和权限。

不要根据 Token 自带的任意 URL 动态下载密钥。签发者和 JWKS 来源必须预先受信。

## 3. Access Token 的资源隔离

一个 API 只应接受明确面向自己的 Access Token。仅验证签名而不验证 `aud`，可能导致其他服务的 Token 被错误复用。

角色映射应采用允许列表：

```text
外部 Claim: ["realm-admin", "orders-reader"]
本地映射: orders-reader -> ORDER_READ
未配置项: 忽略
```

不要把外部字符串直接变成本地管理员权限。

## 4. Refresh Token

Refresh Token 生命周期更长、价值更高，应：

- 只发给确有需要的客户端；
- 对 Public Client 使用轮换与重用检测；
- 安全存储，禁止进入 URL 和日志；
- 与客户端、用户会话和授权范围绑定；
- 支持撤销和异常使用检测。

## 5. 缓存与密钥轮换

JWKS 缓存需要在可用性与安全性之间平衡：

- 正常情况下按 HTTP 缓存语义刷新；
- 遇到未知 `kid` 可触发一次受控刷新；
- 防止每个无效 Token 都造成远程请求；
- 保留短期旧密钥以完成平滑轮换；
- 超过可接受陈旧时间后失败关闭。

## 6. 检查点

能写出完整 JWT 校验清单，并解释为什么“签名有效”仍不足以接受 Token。
